# Canonical Dashboard Workflow

Use this skill for dashboards whose visible data is generated from Markdown/YAML registries, control files, or per-item detail sheets. Keep canonical files authoritative and treat `publicacao/` as derived output.

## Procedure

1. **Register the request and define acceptance criteria.** Record the request in the project queue and internal task summary before editing. State the source of truth, affected routes, expected groups/counts, and required local/public verification. When resuming interrupted work, inspect the live queue, source files, generated outputs, and `git status --short`/diff before deciding what remains; a carry-over checklist is an index, not proof of current artifact state. Preserve pre-existing changes and update only layers actually found stale (monthly control, global control, canonical input, generated family, dashboard), verifying each independently. If a read-only lookup or skill reload is blocked by a duplicate-read/idempotency guard, do not repeat the same call: it blocks only that lookup, not the task. Reuse content already returned in this session; make one different permitted lookup only if an acceptance-critical fact is still missing; otherwise inspect live state and continue the already-authorized steps. Do not abandon an authorized task, claim it is blocked, or ask the user to repeat “continue” solely because a redundant read was denied. Stop only when an essential fact or decision remains unavailable. This does not bypass explicit read-before-write gates.
2. **Inspect sources before editing UI.** Locate the canonical registry and detail files. Decide which fields are authoritative, which may be enriched, and what must remain unknown.
3. **Map records by stable identifiers.** Prefer card/account final digits or IDs; use normalized names only as fallback. Preserve original display values.
4. **Parse fields by key cells.** Match the requested table key and its value cell, not a word anywhere in the line. Normalize Markdown decoration for lookup while preserving currency strings, names, statuses, and identifiers exactly.
5. **Enrich conservatively.** Fill only explicit missing sentinels such as `Não informado`, em dash, or empty. Never overwrite a populated canonical value with a stale or ambiguous detail value. Do not publish full private detail files.
6. **Render from the model.** Derive grouping and counts from the parsed model; do not duplicate business lists in HTML and JavaScript. Show missing data honestly.
7. **Test the behavior.** Cover a stable-identifier match, an extracted field, an intentionally missing field, a non-match/conflict, and group/count totals. Run the full suite and syntax checks.
8. **Regenerate officially.** Never hand-edit derived HTML or JSON. Run the generator, inspect representative JSON values/counts, and verify affected local routes return HTTP 200. When a dedicated `servidor_local.py` exists (e.g. serving `publicacao/` on a specific port), always run it instead of a generic `http.server` to preserve custom MIME, CORS, and root fallback routes.
9. **Verify public output.** Query the active tunnel API (`http://127.0.0.1:4040/api/tunnels`) for the current URL, then request every affected public route and assert HTTP status plus a distinctive change marker. On ngrok tunnels, always pass the header `-H "ngrok-skip-browser-warning: 1"` in automated curl probes to bypass the interstitial warning page and inspect the actual payload. Re-probe the URL immediately BEFORE quoting it in a reply to the user — free-tier URLs rotate on every daemon restart, so a URL verified hours earlier is often already 404; after relaunching the tunnel, update every standing link reference (AGENTS docs, board links, memory) with the new URL. Never reuse a stale free-tier URL.
10. **Close with evidence.** Update task records with real counts, route results, current public URL, and remaining visual-review limitations.

For multi-page screens (an index plus one page per record, a filter that selects the page), the sources-and-pages recipe, the accent pass, and the browser verification loop are in `references/multi-page-dashboards.md`. For a full-project QA pass over an already-built dashboard (suite + build + static sweep + browser + mobile + data anchors), follow `references/qa-pass.md`; when the ask is to revise the numbers/formulas/results themselves, that same file has a numeric-audit recipe (reconstitute the canonical series from the plan's own documented rules and reconcile every published anchor against it).

## Always-on rules

- Markdown/YAML canonical sources are the source of truth; generated pages are views.
- Whole-line matches are not field extraction evidence; headers and narrative rows can contain the same words.
- Never infer limits, dates, or statuses from unrelated text.
- Prefer one shared parser/model over page-specific copies.
- Public artifacts contain only the minimum fields required by the screen.
- If a correction changes a semantic category, update parser/model and tests, not only the label.
- A passing local server does not prove the tunnel serves the new build.
- New `build_*` functions follow the existing convention: same module as the other builders, own `src/<nome>_template.html` + `src/<nome>.js` (template becomes `<nome>.html` on copy), state exposed under a new top-level JSON key, page renders it. Do not invent a second pipeline.
- Page parameters (which record/section to open) travel in markup, never in an inline `<script>`. The ngrok-free tunnel injects a CSP that blocks inline scripts AND inline styles — both `<style>` blocks AND `style="..."` attributes: `window.X = '...'` never runs (page silently falls back to its default view), and inline styles are dropped so server-rendered styling (progress bars, accent font sizes) renders identical or unstyled through the tunnel while looking fine on `127.0.0.1` — an easy trap when QA is local-only. Data-driven widths therefore cannot be `style="width:X%"`: pre-generate a CSS class per value (`.gc-w-23_8 { width:23.8% }`) into an external stylesheet the generator rewrites idempotently alongside the data, and gate the build on ANY `style="` surviving in published pages OR generator sources (same failure style as the menu gate). Keep parameters in `<body data-alvo="slug">` (read `document.body.dataset.alvo` in the shared JS) and keep every CSS rule in external files. When a CSS change ships, bump every stylesheet URL with a build version (`href="x.css?v=<build-id>"`) or the user's browser cache serves the old stylesheet and the fix looks not applied.
- Parsed canonical rows may hold `Decimal`; wrap row values in `float()` before arithmetic in a new builder, or the first subtraction raises `TypeError: unsupported operand type(s) for -: 'decimal.Decimal' and 'float'`.
- Dashboard display text is pt-BR **with accents**; slugs and file names stay ASCII (`demissao`, `contas-cartoes`). Keep slugs, `fonte` and `fonte_path` out of any accent-rewriting pass.
- Source identification on the page: the body shows only the canonical file **name**; the absolute directory appears exactly once, in a single shared field rendered in the footer.
- Money parsing and formatting live in ONE shared helper: a single `brl()` that quantizes with `Decimal(str(v)).quantize(Decimal('0.01'), ROUND_HALF_UP)` (float `round()` is HALF-EVEN plus binary artifacts — the same value can differ by 1 centavo between a text label and the JSON number), and one token parser where the thousands rule lives once: `.` is a thousands separator ONLY in `\d{1,3}(\.\d{3})+(,\d{2})?` — `R$ 1.500` is 1500, not 1.50 (a 1000x error that silently rewrites budget ceilings).
- Every bug fix ships with a regression test written FIRST and proven to fail on the buggy code — and the test must assert the exact field that broke: a fixture that parses the row but never asserts the broken field (e.g. its `status` column) is how an active production bug passes CI for weeks.
- A parser may never discard an unparseable row silently: skip with a stderr warning (a `data: None` row aborting the whole ETL, or a pt-BR value dropped from the aggregation page, is data loss nobody sees). Surface unparseable real rows as visible pendências, not as absence.
- Gate false-negatives are bugs: a validation whose two sides come from the same variable (`abs(x - round2(x)) <= tol`) always passes — compare against the canonical constant; an unreadable page must count as divergent (`ilegivel:<name>`), never be skipped; compare ALL headers of a page (`findall`), not just the first match; an open tag without its closing pair must FAIL the build, not make the rewrite a silent no-op (old nav stays + new nav injected = duplicate shell).

## Common pitfalls

- **Whole-line regex extraction:** can capture `Valor` from a table header or `Valor utilizado` instead of the requested available limit. Match the first cell as the field key and the second as its value.
- **Identifier normalization leakage:** can alter names or currency strings. Normalize only for matching and retain source strings for display.
- **Canonical overwrite:** can replace a current registry value with an older detail value. Enrich only explicit missing sentinels.
- **Stale tunnel verification:** can return an unrelated application or old HTML. Query the tunnel endpoint and assert a page-specific marker. Pass `-H "ngrok-skip-browser-warning: 1"` to prevent false assertions against the free-tier interstitial page.
- **Subset-only sync gate:** a menu/header sync check that validates only the pages it was written for reports OK while the rest of the site keeps the old shell, and the user sees the inconsistency that the gate missed. Enumerate EVERY published page, fail on missing header, and derive expected counts from the generator's page registry (never hardcode them — the count changes with each new page).
- **Header parity without script inclusion:** a shared menu whose interactive behavior (search shortcuts, Esc/click-outside close, active-link fallback) lives in one external JS can pass a header-parity gate on every page while the `<script src>` is emitted only by the newer generators' code path. Native `<details>` keeps navigation working, so the dead search/close/fallback features go unnoticed — until a user presses the shortcut. Gate on BOTH the header markup AND the script tag for every published page, and gate the cache-bust query on the script with the same build id as its stylesheet. After the final template or JavaScript edit, rerun the full generator; inspect the generated HTML for the versioned URL, then fetch the exact referenced asset and assert a marker from the new code. A source-template assertion or isolated unit test does not prove the browser received the current asset.
- **Marker matched by substring:** detecting a build marker with `'marker' in html` or `'.marker' in html` silently passes empty in two ways: rendered page text can cite the identifier (task titles, docs rendered into the page make the string "present" with no real element), and a CSS-selector string (`.marker`) never matches the HTML attribute (`class="marker"`). Detect by attribute regex (`class="[^"]*\bmarker\b[^"]*"` or `<script src="marker\.js[^"']*") — a gate built on naive substring checks validates nothing and reports OK.
- **Shared shell applied per-template:** when one template gets the shared header but the generator also writes other pages by different code paths, only post-processed templates update. Apply the shell through a build-time post-processor (replaces old nav, injects header + stylesheet link, extracts inline `<style>` to external CSS) that runs LAST in the generator, after every write, and is idempotent (`ja-mg`/already-done status) so re-runs are no-ops.
- **Sub-generator pages bypassing the post-processor:** a build whose index/detail pages come from a separate sub-generator (scenario index, detail pages with breadcrumb) must call that sub-generator BEFORE the final post-processor that stamps cache-bust versions and injects shared JS — the sub-generator emits bare tags, so any page it writes AFTER the stamp step is published unversioned and script-less, and the next full build silently differs from the last one. Its internal per-page gates are also meaningless mid-build (they see only the pages written so far — expect `sem-header` noise there): never let the build's verdict rest on a gate that runs inside a sub-generator; the authoritative gates run after ALL pages are written and post-processed.
- **Generator/template drift after menu changes:** run the template-menu updater BEFORE the main generator (it only rewrites templates, never built pages), and on divergence between regenerated pages and templates clear `__pycache__` and regenerate — stale bytecode makes builds diverge with no code change.
- **Serving root vs publicacao directory:** running a generic HTTP server at the project root instead of pointing to `publicacao/` (or using the project's `servidor_local.py`) causes 404/500 errors on routes expected by client-side assets and relative links.
- **Derived-output drift:** can make a manual HTML fix disappear on regeneration. Change parser/template/source and regenerate.
- **Bulk rewrite that silently no-ops:** replacing a template string that still holds its `{placeholder}` (or a `\u`-escaped sequence) against the concrete generated files matches nothing and reports success. After any scripted multi-file edit, assert the new marker is present in every file (`assert 'data-alvo=' in t`) and grep the copied output in `publicacao/` — never trust the loop's own print.
- **Truncated code payload:** appending a very large builder through `execute_code` in one shot can arrive cut off (`SyntaxError: unterminated triple-quoted string`). Write in chunks of a few thousand characters, appending each to the module and running `py_compile` between chunks, and keep the arithmetic in Python rather than in the page JS.
- **DOM read from the wrong tab:** after navigating, a `js()` probe can evaluate in a previously opened tab, so a page that renders correctly looks broken (its `<title>` is right but the DOM reads as the old page). Assert `document.title` first, call `ensure_real_tab()` when tabs disagree, and treat DOM assertions — not screenshots — as the evidence when the screenshot capture times out.
- **Plausible page, wrong number:** the canonical plan may count an item the user has decided not to pay as a paid expense. Show both figures side by side (the plan's hole and the real hole) with the one-line explanation, instead of publishing the plan's number as the current situation.
- **Component quoted as the total:** a reserve with a locked slice (e.g. an investment partially blocked by a court order) has THREE distinct numbers — total, locked, available (= total − locked) — and a one-liner that cites the locked part as the reserve's whole misstates it even when every engine computes correctly. When the user states a real balance, reconcile it against the canonical triple and grep plan summaries and KPI labels for component-as-total confusion; fix the label to carry all three (total (available X · locked Y)).
- **Superseded-engine numbers on a page:** scenario/reference cards with hardcoded values drift silently behind the canonical engine — a value nobody recomputed keeps rendering after the canonical motor changes, and a page that cites the canonical doc's name while showing another engine's numbers misleads more than an empty state would. The drift can also hide inside the dashboard's OWN reimplemented formula (a copied `simulate()`), not just in card literals — diff the published series against the canonical engine line by line, not only the display cards. Named-scenario cards must read the canonical engine's computation (import its `calcular()`/equivalent in the same build, no staleness window); a variant engine's result keeps the variant's label and an `estimate` flag, never the canonical scenario's name.
- **Shared constants with importers:** an engine's named constants often serve as parity-tolerance references inside other engines that import them — grep importers (not just usages) before changing a value, and align the constant to the canonical doc (e.g. a "total" that no longer equals the sum of its monthly parts) rather than patching display strings around it.
- **Generator input from ephemeral cache:** a canonical generator that reads its engine payload from a scratch/cache path dies silently once the platform prunes that directory (hours-to-days TTL), leaving the source of truth unregenerable from the repo — nothing in the code shows the dependency until it breaks. Read inputs from durable sources, ideally the canonical file's own YAML block (self-contained: input + output in the same document), so one script run reproduces the whole family from the repo alone.
- **Two writers for one canonical family:** when a canonical file has generated companions (.json/.csv/.xlsx), every second entry point that also rewrites them (an old engine's `main()`, ad-hoc export scripts) is a drift vector — last writer wins and nobody notices. Make ONE script the single writer and hard-disable the others (`raise SystemExit(...)` at the top of the old entry point) while keeping their library functions (`load_config`/`simulate`) importable for the engines that consume them.
- **Auxiliary tables leak into generic row parsers:** a cadastro parser that accepts any table row with ≥N columns outside known sections swallows appendix tables in the same MD (a payments-history table turns into bogus records like a `Data` header row), inflating counts and failing identifier tests. Gate row capture by SECTION marker (skip `📋`-type appendix sections and header words like `Data`), and derive semantic groups from the section a row came from (the calota/blacklist section → 'Pagamento posterior'), never from a hardcoded card-name list — the group assignment silently misses cards when the registry adds one.
- **Renaming a canonical file strands its pointers:** a horizon/name migration leaves living references far beyond the repo — sibling generators, control indexes, skills, AGENTS/CLAUDE docs, test fixtures — and the app keeps silently reading the old file. After the move, grep the whole estate for the old name and classify every hit: living pointer (fix), historical provenance (changelog/comment citing origins — keep), archived copy (leave in the archive dir). Re-run dependent generators and the full test suite before declaring the migration done.
- **Identifier gate trips on the redaction text itself:** narrative fields in canonical MDs (e.g. a payment method line citing branch/account numbers) flow verbatim into the public JSON through generic text-field parsers; a privacy gate banning those words is correct. Mask at the SOURCE MD — and write the replacement without the banned token: a redaction note like 'branch/account data omitted' still contains 'branch' and keeps the gate red. If a mask edit doesn't turn the suite green, re-dump the model and locate the next occurrence instead of assuming the gate is flaky.
- **Sync gate hashing raw header HTML:** a menu-parity gate that hashes headers verbatim false-positives forever once per-page state (active-link class, drawer) differs — it reports the site broken while it is consistent, and a gate that cries wolf stops being trusted. Hash only the state-independent skeleton (normalize active-class/drawer state before comparing) and gate on what the build actually guarantees. The normalizer must strip EVERY emitted form of that state: the same nav often writes the active marker as a full pair on one copy (`class="mg-ativo" aria-current="page"`, desktop) and as the lone class on another (`class="mg-ativo"`, drawer copy, by a11y design) — stripping only the pair leaves each page's hash stamped by its own alvo and the gate fails permanently. Unit tests hide this when their fixture generates every page with the SAME alvo; test the normalizer across distinct alvos.

- **Status column by fixed cell index:** reading the status from `cells[2]` when the canonical table has 4 columns (`| # | Cartão | Valor | Status |`) publishes the VALUE where the status belongs — parse columns by header name with a last-cell fallback.
- **Negation matched as affirmative:** `re.search(r'✅|pago', status)` matches the `pago` inside `Não pago` / `Ainda não pago`; check negations (`não pago`, `❌`) BEFORE the affirmative keyword, or one status edit publishes an unpaid bill as paid. Same family: deriving a due-date year from a fixed literal (year 2026 for a `10/01` venc under competência `Jan/27`) flags future bills as overdue — derive the year from the competência string.
- **Eternal-union ETL keyed by process TZ:** SQL like `date(ts,'unixepoch','localtime')` follows the process timezone — under a TZ change, records near midnight re-key to a different day and an append-forever union permanently double-counts the split day (or loses half of it). Fix the TZ in the SQL itself (`'-3 hours'` for BRT), never via `localtime`.
- **Append-only file without dedup marker:** appending a section to a canonical MD while regenerating from a JSON cache means a corrupt/missing cache regenerates ALL closed months and re-appends them — sections double every run. Check for the section's marker (`## Análise de {rotulo}`) before appending.
- **Declared-but-empty column in a sibling format:** a CSV column written empty in every row while the MD/XLSX carry the series is a cross-format inconsistency that audits miss — populate from the existing in-module series. Same honesty family: a provenance label claiming `120 months applied` when the loop only had 108 must report applied-vs-requested.
- **Subagent completion report taken as verified:** a truncated subagent's "163/163 green, pushed" is a self-report — confirm `git log`, `pytest` and `git status` yourself before reporting to the user; waves arrive with valid code but NO commit and the parent must commit and finish the remainder itself.
- **Audit and fix phases overlap on one repo:** fan out bug audits in parallel but mark every audit dispatch READ-ONLY (proofs executed in `/tmp` or as read-only queries; deliverable is a numbered inventory with executed evidence, not edits); each fix wave touching the same tree runs SEQUENTIALLY and only after ALL audits return — a fixer editing files an auditor is still reading invalidates the findings.
- **Fix wave dispatched without its patch map dies at the iteration cap:** a leaf given only the goal burns its iterations re-reading files to rediscover what the audit already mapped, and dies with valid, uncommitted work in the tree. Embed the COMPLETE map in the dispatch context — file:line, the edit itself, the exact regression-test name per item — plus the instruction to apply patches directly, re-read at most one file per file touched, and commit incrementally every couple of items. When a wave truncates anyway, the parent finishes it: check `git status` and the group tests, commit what is ready, and complete the remainder itself (cheaper than re-dispatching).
- **Suite run via the wrong interpreter:** invoking the suite as `python3 -m pytest` under the currently-active venv can hit a `ModuleNotFoundError: pytest` that reads exactly like a broken suite — run the `pytest` CLI on PATH (`~/.local/bin/pytest`) or the project's interpreter that actually has it.
- **Test pins an old canonical count or number:** a test asserting a fixed count of parsed items or a financial anchor can become stale when the canonical source legitimately changes. After running the official writer, run the full suite and search the entire test tree for prior anchor values; recompute each candidate against the named current engine/output before editing. Update only assertions intended to describe the current canonical series, retain assertions explicitly documenting legacy provenance, and never bulk-replace values or loosen count assertions to ranges—either shortcut can hide real regressions or erase historical distinctions. Attribute the failures before editing anything: rerun the suite with the in-flight diff stashed (`git stash push -m <label> -- <files>`) — same failures with and without your diff prove they are data-acoupling, not regressions you introduced. Recalibrate coupled tests with a scripted EXACT-COUNT replace (apply each substitution only when the file contains exactly one occurrence of the old string; log and abort that item otherwise) — blind `str.replace` silently rewrites the wrong anchor or misses a variant, and the suite then 'passes' against edits nobody reviewed. Before calibrating a sibling wave's untracked test around an assumed state (e.g. a TDD expecting a partial payment), verify the current payment evidence first — the assumption may already be obsolete (bill paid in full) and the test must be rewritten to the real state, not implemented toward it.
- **Regenerating dashboard data from inputs without verifying target:** when asked to update the dashboard with new financial numbers, editing a script variable alone does not prove the value appears anywhere reachable. Always confirm the full chain: edit input → run `gerar_canonico_2036.py` to update `FLUXO-CAIXA-2026-2036.json` → run `gerar_dashboard.py` → query the published `evolucao_2036.json` (the actual data source used by `evolucao_2036.html`) rather than grepping raw HTML for money strings. Use a small Python `json.load` call to read `publicacao/evolucao_2036.json` keys and assert the updated field exists; HTML may not render BRL-formatted currency as a simple substring.
- **Generator location assumptions:** don't assume the generator lives in `src/` — check the repo root first (`ls *.py`) before declaring a file missing; projects keep the entry-point script beside the templates it drives.

## Verification checklist

- [ ] Request registered before implementation
- [ ] Canonical and detail sources identified
- [ ] Stable-identifier matching tested
- [ ] Missing-field behavior tested
- [ ] Group/count totals tested
- [ ] Official generator run
- [ ] Full tests and syntax checks passed
- [ ] Affected local routes returned HTTP 200
- [ ] Affected public routes returned HTTP 200 and contained a change marker
- [ ] Task records updated with evidence
